## Design decisions

- **Single-file skill.** All runtime rules are in `SKILL.md` (4,985 `o200k_base` tokens, 177 lines). Whether bundled reference files can be read reliably is unverified.
- **No runtime script.** Code in a skill cannot see the conversation buffer; a script would only see text the model re-typed into it. The JavaScript in `dev/src` is a reference implementation for tests and is not shipped.
- **No `agents/openai.yaml`.** It is optional and documented for Codex UI metadata, and implicit matching must stay on so the literal `/contextestimate` can reach the skill.
- **Measurement priority:** host telemetry (none exists, so normally skipped) → tokenized transcript the user supplied → visible-text heuristic.
- **Budget:** see the next section. A valid `limit=N` means `^[1-9][0-9]*$`.

## Policy change: default-budget guidance

**What changed, and why.** Until this version an unknown model window prevented a handoff assessment: with no documented Work window the report showed `Planning risk: UNKNOWN (model window unknown)` (or `not documented`, `not recognized`, `ambiguous`) and said "a model-relative handoff assessment is unavailable", asking the user to re-invoke with `limit=N`. Only GPT-6.1 Sol has a documented Work window, so almost every report on another model gave no guidance, even for a five-message chat. This is a deliberate product-policy change: unknown model capacity is now reported separately (on the `Model:` line), and the guidance uses an explicitly labeled planning budget.

- *Four concepts kept apart:* (1) the estimated accessible text; (2) the planning budget that scales the bar and drives the guidance; (3) the model's documented Work window, if any; (4) actual backend usage and remaining capacity, which stay unknown.
- *Precedence unchanged:* valid `limit=N` → valid `saved_limit` → current documented or live-checked Work window → 128000. The fallback is renamed from "conservative baseline" to **default heuristic**: 128k is not documented for any Work model and is not universally conservative (a real window may be smaller). The config key is now `default_budget`. A derived or default budget is never saved into `saved_limit`.
- *Thresholds unchanged, reframed:* 50/70/90 apply to whichever budget is selected, including the default (a ~5k chat against 128k is LOW, "Continue normally."). They are described as handoff-planning policy, not validated capacity thresholds, and the label is **Handoff priority** (was `Planning risk`), which says how soon to plan a handoff rather than claiming a measured risk.
- *Removed:* the per-state model recommendations and risk reasons (`model window unknown`, `model window not documented`, `model not recognized`, `model ambiguous`) and the retry-flow wording. `model=` and `limit=` stay documented as optional controls. The model state no longer changes the priority or the recommendation; only the budget source and its note differ.
- *Kept:* partial or summarized history and unmeasured attachments still give `UNKNOWN (...)` and a recommendation to consider a handoff (escalating with the counted share under every budget, now including the default); `UNKNOWN (no defensible text estimate)` when no magnitude can be justified; no inferred truncation; no reconstruction of history; backend usage never treated as measured; `/handoff` never run. Model resolution, the registry, freshness handling, and the lookup acceptance rules are unchanged, and an unknown, ambiguous, unrecognized, or absent identity never blocks guidance.
- *Search results are not conversation text:* a search done during the invocation to establish the budget is excluded from that invocation's estimate (SKILL.md step 4.3; `thisInvocation` messages in the reference estimator), and the skill says a search happened only if it actually used a search tool. The lookup notes now read "An official-source search found no ChatGPT Work window for <Model>." and "No search tool was available, so <Model>'s Work window was not looked up."
- *Report layout:* `Planning budget: <value> (<source>)`, `Model: <name> (<source>) — <status>`, the bar line `~N% of planning budget`, `Handoff priority: <level>`, a blank line, then `Recommendation:`. Notes: "Guidance uses a heuristic planning budget; actual model capacity and backend usage are unknown." (default), "Guidance uses your planning budget; …" (user or saved), "Guidance uses the documented Work window as the planning budget; backend usage and remaining capacity are unknown." (documented), and the over-budget note at or above 100% under any budget.
- *Size:* removing the per-state recommendation text brought `SKILL.md` from about 5.5k back to 4,985 `o200k_base` tokens, and the package test again enforces the spec's < 5,000 recommendation.

**Tests for the change.** `model-limit.test.js` (default budget at every share, including the 50/70/90 boundaries, and incomplete coverage under the default), `model-resolution.test.js` (every `Model:` state gives the same LOW guidance; only the budget differs), `invocation.test.js` (a plain invocation gets full guidance; no report asks for `model=` or `limit=`), `registry.test.js` (undocumented and stale rows use the default with ordinary guidance), `greeting.test.js` (greetings on undocumented models are LOW), `model-resolution.test.js` again (switching between two undocumented models changes only the `Model:` line; this invocation's search results are not counted), `spec-sync.test.js` (SKILL.md wording, no "conservative" or old labels), and scenarios `undocumented-5k`, `default-budget-high`, and `search-result-excluded` for the grader, which now rejects `UNKNOWN` caused only by an unknown window and the old labels. Obsolete assertions that expected `UNKNOWN` only because of the window were replaced.

**Not verified in ChatGPT Work.** The new policy has only been checked locally against the instruction text and the reference implementation; it has not been uploaded or run in ChatGPT Work.

## Planning budget, model evidence, and model switches

The skill separates the four concepts above. Percentages and bars always refer to the planning budget.

**Source and verification.** The one documented window used is the 500,000-token default for GPT-6.1 Sol in ChatGPT Work and Codex, from <https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex>, verified 2026-10-23 (`DOCUMENTED_SOURCE` in `dev/src/policy.js` and the registry in `SKILL.md`). Normal invocations never browse to look it up, so after OpenAI changes that page, the skill text must be updated and the ZIP re-uploaded. Not generalized: no other model's window is stated on that page, API specifications are not substituted for Work limits, and no hidden-overhead deduction or usable-input budget is invented.

**Precedence and labels.** (1) valid `limit=N` → `user budget`; (2) valid `saved_limit` → `saved user budget`; (3) a documented Work window for the model identified by current evidence → `documented GPT-6.1 Sol Work window, checked 2026-10-23` (a live check: `<Model> Work window, live check`); (4) otherwise 128000 → `default heuristic`. Only (3) is a model window, and none of them is remaining capacity. An inferred model, a model-derived budget, or the default is never written into `saved_limit`.

**Model evidence, re-resolved on every invocation.** Accepted: trusted runtime metadata that identifies both the model and the Work surface, or a `model=MODEL_ID` assertion in the invoking message's first line (a user assertion, not detection). Not accepted: the assistant's self-identification, the local Claude CLI model, an earlier invocation's assertion or derived budget, a model name in quoted, pasted, summarized, or tool content, the plan, the task type, or an assumption that no switch happened. With no evidence the skill uses the user budget or the default; a pinned budget is the same before and after a switch and is never described as the new model's capacity. Switching between two undocumented models gives the same default budget and the same guidance.

**Re-estimation.** The skill re-estimates the content accessible now. It carries no running total across model switches or compaction, and a changed estimate after a switch is not explained as a backend change.

**Report layout history.** `Configured context limit` / `Estimated usage` became `Planning limit` and `~N% of planning limit`, then `Planning budget` and `~N% of planning budget`; `Estimated visible context` became `Estimated accessible text`; `Risk` became `Planning risk`, then `Handoff priority`. Genuine host telemetry, if a platform ever supplies measured usage with its own limit, uses a separate host-reported layout.

**No cross-model accuracy guarantee.** The estimation rates were calibrated against one tokenizer (`o200k_base`) on small synthetic texts, are applied by the model's judgment, and are not validated for any particular Work model.

## Work model registry and freshness checks

**Sources read (2026-10-23).** [ChatGPT Work and Codex](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex) (Help Center, showing "Updated: 5 hours ago" when read) and [Models](https://learn.chatgpt.com/docs/models) (ChatGPT Learn, no date shown).

**What they say.** The Help Center article: "GPT-6.1 Sol, GPT-6 Sol and GPT-6 Luna are models for ChatGPT Work and Codex. They are not available in regular ChatGPT conversations." and "GPT-6.1 Sol has a default context window of 500,000 tokens in ChatGPT Work and Codex." It also says availability depends on plan, workspace settings, and rollout, mentions GPT-6 Astra in Work and Codex for Plus (and GPT-6 Pro, powered by Astra, in ChatGPT for higher plans), and gives no window for any other model. The Learn page names Astra, GPT-6.1 Sol (`gpt-6.1-sol`), GPT-6 Sol (`gpt-6-sol`), GPT-6 Luna (`gpt-6-luna`), and says GPT-5.6 Sol, Terra, and Luna "remain available during the rollout"; it states no context window for any model and gives no Astra ID. Retired or retiring Codex models it lists (GPT-5.5 for ChatGPT sign-in from 2026-10-14, GPT-5.4 and 5.4 mini, GPT-5.3-Codex-Spark, GPT-5.3-Codex, GPT-5.2) are not in the registry. GPT-6 Pro is described for ChatGPT broadly rather than scoped to Work, so it isn't either.

**Registry in `SKILL.md`** (mirrored by `MODEL_REGISTRY` in `dev/src/policy.js`, with tests keeping them in sync): `gpt-6.1-sol` 500000; `gpt-6-sol`, `gpt-6-luna`, GPT-6 Astra, GPT-5.6 Sol, GPT-5.6 Terra, GPT-5.6 Luna: not documented. Each row carries its source URL (as the tag H or L, defined once) and the date checked. **Undocumented windows: every entry except GPT-6.1 Sol.** Astra and GPT-5.6 have no documented model ID, so they match only by normalized name (`gpt-6-astra`, `gpt-5.6-terra`); no ID was invented.

**Rules.** A listing is not an availability claim: availability varies by plan, workspace, role, and rollout. A window is an exact number only if an official source explicitly gives a ChatGPT Work or Work-and-Codex value; it is never inferred from API documentation, output limits, usage allowances, credit rates, or a model in the same family, and rows are not added from memory. Normal estimates never browse. Conditional lookup (only if web search is available): the user explicitly asks for current model/window information; the model identified by current evidence is not in the registry; that row is more than 90 days old (an unknown date counts as fresh), or this invocation's `model=` names a recognized model with no documented Work window (a targeted search for that exact model's ChatGPT Work context window; a model from runtime metadata, or a bare invocation, never triggers it). A lookup never decides which model is current. Its result applies to that invocation only, is labeled `<Model> Work window, live check`, and is never saved or described as an update to the skill. Accepted only if the official source (help.openai.com, learn.chatgpt.com, openai.com) explicitly scopes an exact number to ChatGPT Work or Work and Codex for that model; API values, output limits, allowances, Codex-only or Chat-only values, other models' figures, and inaccessible or ambiguous sources are rejected. A registry window older than 90 days that is not reconfirmed is treated as unknown (default budget, plus a note), so the installed skill falls back to the default heuristic rather than trusting an old number; `limit=N` or a refreshed upload fixes that. Model identity evidence is unchanged (`model=MODEL_ID` is a user assertion unless trusted runtime metadata supplies the model and the Work surface).

**Size.** The registry and rules first pushed `SKILL.md` past the Agent Skills spec's recommended 5,000 tokens (about 5.6k); it was trimmed to about 4.98k `o200k_base` tokens by defining the two source URLs once, merging the GPT-5.6 rows, condensing the "what the number is" subsection, and removing the size anchors, the separate sanity-check paragraph, the worked partial-coverage example, and duplicated sentences. The model-resolution update (a Model line with six statuses, a risk reason and recommendation per unknown state, the model-name parsing rules, and the targeted lookup) brought it to about 5.5k tokens, over that recommendation again. The package test temporarily enforced a ceiling of 5,600 tokens. The default-budget policy change removed the per-state recommendations and brought `SKILL.md` back to 4,985 tokens, so the test again enforces < 5,000 (and the <500-line limit). This is a recommendation in the spec, not a ChatGPT limit that has been observed, but a larger skill costs more context per use and could make counting the skill's own text (a hypothesis in the second live regression below) more likely.

**Tests.** `dev/test/registry.test.js`: the registry table in `SKILL.md` matches the reference registry row by row (window, source URL, date); known model (Sol 500k) and undocumented models (baseline, no lookup needed, no family inference); Work-versus-API scoping (API, Codex-only, Chat-only, output-limit, allowance, unscoped, non-official hosts, non-integer windows, wrong model); stale, unavailable, and API-only sources; accepted live values applying to one invocation without touching the registry; model assertions and runtime metadata unchanged; and that ordinary estimates need no lookup (and the reference code has no network access).

**Not verified in ChatGPT Work.** Neither the registry values nor the live lookup have been uploaded or exercised in ChatGPT Work. Whether Work offers web search to a skill, how it presents lookups, and whether it follows these rules are unknown; the tests check instruction text and a reference implementation only, and no lookup was run through the skill.

## Model resolution in the report (third live finding)

*Historical record. The parsing, matching, `Model:` line, and lookup rules below still apply; the per-state risk reasons and recommendations were removed by the default-budget policy change above, and the `Model:` line wording was shortened.*

**Observed (ChatGPT Work).** With GPT-6.1 Sol selected and no `model=`, the skill reported the registered 500k default. With GPT-6 Sol, GPT-6 Luna, GPT-6 Astra, and GPT-5.6 Terra it reported the 128k baseline and `UNKNOWN`, including for `/contextestimate model= GPT-6 Sol`, and told the user to invoke again with `model=MODEL_ID`. The tester pointed out that these results could not show whether an undocumented model name was parsed or recognized.

**Diagnosis (from the code and rules, not from a live trace).**

- `model=` was read as a single whitespace-free token (`model=(\S*)`). `model= GPT-6 Sol` yielded an empty value and was dropped as if no model had been given, and a multiword display name could never match. A bare `model=GPT-6` would have kept only the first word.
- Every outcome without a documented window (a recognized GPT-6 Sol, an unrecognized name, no model at all) produced the same baseline report, the same `UNKNOWN (model window unknown)`, and the same advice to repeat `model=MODEL_ID`, which cannot help when OpenAI publishes no window for that model.
- The Sol result with no `model=` shows the model was identified some other way. The skill's rules accept only trusted runtime metadata, but whether that or the assistant's own self-identification (which the rules reject) was used is not established by the observation.

**Changes.**

- *Parsing.* `model=` takes the rest of the first line up to the next `limit=`, `bar=`, or `model=`; whitespace around `=` is allowed; surrounding quotes, backticks, and curly quotes are removed; case, spaces, hyphens, underscores, and the non-breaking hyphen OpenAI's pages use are normalized.
- *Matching (aliases only where unambiguous, no invented IDs).* A value matches a registry row by ID, full name, name without `GPT-` (the Learn page's "6.1 Sol", "6 Luna"), or the official short label "Astra", optionally followed by a reasoning effort as the model picker shows it ("GPT-6.1 Sol Medium"; the efforts listed are light, low, medium, high, extra high, xhigh, max, ultra). Words that are only part of registry names ("Sol", "Luna", "GPT-6", "Terra") are `ambiguous` and list what they could mean; anything else (including real models outside the Work registry such as GPT-6 Pro, and names with extra words like "GPT-6 Sol Turbo") is `unrecognized`. Astra and GPT-5.6 have no documented ID, so none was added.
- *Report.* A `Model:` line after the limit line states the source (`supplied by you with model=` or `from trusted runtime metadata`; a user-supplied name is never "detected") and the status (recognized with a documented window, recognized with a window from a live check, recognized with no documented Work window, recognized but the registry window is stale, not recognized, ambiguous, or not identified). The planning-risk reason is per state: `model window unknown` (no model, or a stale window), `model window not documented`, `model not recognized`, `model ambiguous`.
- *Recommendations (baseline only; partial-history and attachment advice is unchanged).* No model: the window is unknown; offers `limit=N` and does not suggest that repeating a model name will reveal a value. Recognized, no documented window: says the model was recognized but no ChatGPT Work window is documented; offers only `limit=N` as the user's own budget, "a planning figure, not the model's actual window". Not recognized: asks for a clearer model name or `limit=N`. Ambiguous: lists the candidates and asks for the full name or `limit=N`. None recommends `/handoff`.
- *Targeted lookup.* An explicit `model=` for a recognized model with no documented Work window triggers a search of official OpenAI sources for that exact model's ChatGPT Work context window, if search exists. The result is accepted only if an official source (help.openai.com, learn.chatgpt.com, openai.com) explicitly scopes the exact number to ChatGPT Work or Work and Codex for that exact model; API-only, Chat-only, Codex-only, output-token, allowance, inferred, ambiguous, or unavailable results are rejected. An accepted value is used for that invocation only, shown as `documented <Model> / Work default; live check`, and never saved to the registry or to `saved_limit`. If nothing suitable is found the report adds "Searched official OpenAI sources for <Model>; no ChatGPT Work context window was found." and with no search "Search is unavailable here, so <Model>'s Work window stays unknown." Ordinary invocations, and models identified from runtime metadata, do not browse.
- Rates, thresholds, the estimate procedure, the registry values (GPT-6.1 Sol 500,000), model-evidence rules, and the partial-history and attachment behavior are unchanged.

**Tests.** `dev/test/model-resolution.test.js` (19 tests) covers the observed `/contextestimate model= GPT-6 Sol` input; GPT-5.6 Terra, GPT-6 Luna, GPT-6 Astra, and GPT-6.1 Sol in many spellings (whitespace around `=`, multiword names, IDs, quotes and backticks, the `6 Sol` and `Astra` aliases, reasoning-effort suffixes, non-breaking hyphens); other options on the same line; ambiguous and unrecognized names; distinct `Model:` lines, risk reasons, and recommendations for every state; the rule that a user-supplied name is never "detected"; lookup triggers, official-source acceptance and rejection, the one-invocation scope, and the "nothing found" and "search unavailable" notes; and that the accessible-text estimate is identical whichever model is named. Eleven scenarios (`model-observed-gpt-6-sol`, `model-gpt-5-6-terra`, `model-luna-backticks`, `model-astra-label`, `model-sol-picker-label`, `model-unrecognized`, `model-ambiguous-sol`, `model-lookup-none-found`, `model-lookup-unavailable`, `model-with-budget`, and the updated `greeting-luna`) feed the behavioral grader. These are automated checks of the parser, the reference implementation, and the instruction text. They do not show that a language model follows the instructions, no live search was performed, and nothing here reads ChatGPT's backend usage or can obtain an unpublished context window.

**Not verified in ChatGPT Work.** None of this has been uploaded or run in Work. In particular, whether Work gives a skill search access, how it shows an `@` mention, and whether a model applies the new parsing and wording as written are unknown.

## Smoke test: greeting across a model switch, and unknown window is not a handoff warning

*Historical record. The neutral "assessment unavailable" recommendation described here was later replaced by default-budget guidance (see "Policy change" above); the sizing findings still apply.*

**Observed (ChatGPT Work, new conversation).** `hi` on GPT-6 Luna Medium → "Hi! What would you like to work on?"; `Hello World` on GPT-6.1 Sol Medium → "Hello, world! 👋"; `/contextestimate` on Sol → `<1k` tokens against the documented 500k Sol / Work planning limit; `/contextestimate` on Luna → `~5k` tokens against the 128k conservative baseline, `UNKNOWN` risk, and "Consider /handoff before substantial work; model window unknown." Neither live number is ground truth.

**Defect 1: an unknown window produced a handoff warning.** The unknown-window recommendation was built like the partial-history one (base chosen by the share of the baseline, plus "; model window unknown"). A share of a window nobody knows is not a threshold comparison, so it should not advise anything. Changes:

- With the baseline as the only reason for `UNKNOWN`, the recommendation is now exactly "A model-relative handoff assessment is unavailable. To compare against a planning limit, invoke this skill again with the parameter in the same message, e.g. `@contextestimate limit=250000` or `@contextestimate model=MODEL_ID`." The bar and percentage are still drawn against the baseline, and the note is the baseline note even at or above 100% (the over-limit note is reserved for known planning limits, so a full bar against an unknown window doesn't suggest the chat is near a limit).
- A handoff recommendation still comes from a known planning limit and its thresholds, or from a separate explicit reason: missing history (`partial history`) or unmeasured attachments keep `UNKNOWN` and "Consider /handoff before substantial work; <what is not counted>." Under the baseline that advice no longer escalates with the baseline share and no longer ends with "; model window unknown" (the label keeps it). With a known limit the share still escalates the advice as before.
- Thresholds and rates are unchanged; recommendations remain advisory and `/handoff` is never run.

**Defect 2: the same tiny conversation was sized ~5x larger on one model.** The accessible text in that exchange is the four short messages plus two invocations and the first report, which is about 150 tokens by `o200k_base` (about 50 before the first invocation's report). ~5k is not a plausible count of that text. The cause is not known. One plausible, unverified explanation is that non-countable material was summed in: the `SKILL.md` under test was about 3.9k `o200k_base` tokens (about 4.2k now, with this fix), and with a system prompt, instructions, memory, and tool definitions the total passes 5k. That is a hypothesis, not a finding, and could equally be run-to-run estimation variability, which a skill instruction can't remove. Changes:

- `SKILL.md` now carries a sanity check: a few short exchanges are at most a few hundred tokens (a four-message greeting is well under 1k); a total in the thousands for such a chat means the skill text, instructions, memory, tool definitions, or reasoning are probably being counted, so recount only message text; the total should not depend on the selected model.
- `dev/fixtures/greeting.js` models the four-message exchange, the two invocations, and the first `<1k` report as visible transcript text only, and lists the non-countable material (system prompt, developer instructions, memory, hidden reasoning, tool definitions, the skill text) separately. `dev/test/greeting.test.js` and two scenarios (`greeting-sol`, `greeting-luna`) check that the exchange stays under 1k (reference estimator and tokenizer), that the non-countable material never enters the transcript, that counting it would inflate the total into the thousands, that Sol → Luna → Sol re-resolves the denominator each time without carrying the old one, that only the denominator differs between the two reports, and that partial-history and attachment behavior is intact under both limits.
- These tests verify the stated counting rules and policy against a synthetic fixture with deterministic utilities. They do not show that a language model produces a deterministic exact count in a live invocation, and no rate or threshold was tuned to this case.

**Model switches.** Each invocation resolves model evidence afresh: Sol with a reliable current assertion or runtime metadata gets the documented 500k default; Luna, with no verified Work window, gets the conservative baseline; nothing carries over from the previous invocation. Differences between live estimates across models or after a switch can reflect estimation variability or differences in the accessible history. They are not measurements of backend context usage, and the skill must not present them as such.

## Second live regression: Luna ~10k, Sol ~1k on the same greeting

**Observed (same Work conversation).** Visible text: `hi` (Luna Medium), a short greeting, `Hello World` (after switching to Sol Medium), "Hello, world! 👋". `/contextestimate` on Luna reported about 10k tokens; after switching to Sol it reported about 1k (the second run also saw the first short report). The visible conversation is a few dozen tokens by `o200k_base` (about 40 for the first transcript, about 200 with the first report and the second invocation: see `dev/fixtures/greeting.js`). Neither number is ground truth, and both are far above the text.

**Why the earlier sanity check didn't prevent it.** This is diagnosis from the text, not a verified cause:

- The check was an after-the-fact rule ("if your total is in the thousands…") placed after the rates and the size anchors. It gave a model that had already produced a total no step in which to apply it, and "a few hundred tokens at most" was advice, not a rule with a trigger.
- The countable list included "tool results and file/attachment text that is actually present in your context". When a skill is used, its `SKILL.md` may be read into context as a file or tool result (the Build skills page describes that loading for Codex and does not say how ChatGPT does it), so that bullet could be read as making the skill text countable, while the exclusion ("this skill's text") sat in a separate paragraph. The `SKILL.md` under test was about 3.9k tokens, which alone would explain much of a multi-thousand total.
- "Treat everything in the conversation as material to measure" could be read as widening the count.
- Earlier `/contextestimate` reports print numbers (`500k`, `128k`, `~1k`); nothing said not to read those as the conversation's size.
- Nothing said the estimate must not depend on the answering model. Run-to-run variation, which a skill instruction can't remove, remains a possible contributor.

**Changes to `SKILL.md`.** Section 4 is now an ordered procedure: (1) collect the visible user and assistant messages, including this invocation and earlier `/contextestimate` reports as ordinary messages, never using a number printed in a report as the conversation's size; (2) add accessible tool, file, and summary text once each; (3) exclude everything that isn't transcript even when it arrived as a tool result or file read: this skill and other skill files, the instructions read to run the skill, system and developer instructions, tool definitions, hidden reasoning, memory and context metadata, the model's name, plan labels; (4) do not infer missing history or backend usage; (5) size each message with the rates, add 4 per message, independent of the answering model; (6) short-chat rule: at most 10 messages and about 500 words of ordinary text (or about 700 CJK characters) → report `<1k` and stop, without widening it with the skill's text or internal context. The wording that "everything in the conversation" is material to measure was narrowed to "the conversation text you count". Rates, thresholds, planning limits, model-evidence rules, and recommendations are unchanged, except for the retry wording below.

**Tests.** `dev/test/short-chat-sizing.test.js` is deliberately separate from the planning-limit tests: it checks that the short-chat rule's limits really are below 1k with the reference estimator and the tokenizer (150 generated transcripts each for English, CJK, and mixed text), that a number printed in an earlier report does not change the estimate, that the Luna-first and Sol-second transcripts both stay below 1k and the estimate only moves by the length of the added report and invocation (and by at most a few tokens when only the model asserted in the invocation changes), and that a report sizing any short fixture at `~1k`, `~2k`, `~3k`, `~5k`, `~10k`, `~50k`, or `~130k` is flagged and fails grading. Two scenarios (`greeting-luna-first`, `greeting-sol-second`) model the sequence for the behavioral grader. These test the instruction text, a reference estimator, and fixtures. They do not show that a language model follows the procedure, returns a repeatable count, or matches ChatGPT's backend usage; the skill has no transcript tokenizer; and no cross-model accuracy is claimed.

**Parameter retry flow (superseded: options are now optional and no report asks for them).** The neutral recommendation then read "A model-relative handoff assessment is unavailable. To compare against a planning limit, invoke this skill again with the parameter in the same message, e.g. `@contextestimate limit=250000` or `@contextestimate model=MODEL_ID`." Rationale: a separate follow-up message containing only `model=...` or `limit=...` is not an invocation and cannot update a previous report, so the user invokes or selects the skill again with the parameter in that same message, for example `@contextestimate limit=250000` (a planning budget) or `@contextestimate model=gpt-6-luna` (an assertion that records the model but, with no documented Luna window, still leaves the baseline). Examples use ChatGPT's documented `@` selection ("In ChatGPT, type `@` to select a skill"; "In ChatGPT Work, invoke it as `@skill-creator`"; checked on the Build skills page, 2026-10-23). `/contextestimate` stays an instruction trigger, not a verified registered slash command. The parser now accepts `@contextestimate`, `/contextestimate`, or both before options on the first line (and bare options only when the platform shows the skill was selected for that message). Each new invocation applies the parameter to that run only, recalculates from the currently accessible visible conversation, and keeps the evidence rules: `model=MODEL_ID` is a user assertion, not detection (and `model=gpt-6-luna` is accepted but leaves the baseline, because no Luna Work window is documented), and `limit=N` is a user planning budget. `dev/test/invocation.test.js` covers the forms, the bare-message case, recalculation, non-persistence, the recommendation text, and the documentation.

**Not verified.** None of this has been run in live ChatGPT. This live case is not fixed or verified until the updated ZIP is uploaded and retested in ChatGPT Work. How Work presents an `@` mention to the assistant (text, a chip, or metadata) is unknown, which is why the skill reads options from the first line of the message that selected it.

## Estimation heuristic

Rates were calibrated against `o200k_base` (via `gpt-tokenizer` 2.9.0) on synthetic fixtures in `dev/fixtures`:

| Content | Rate |
| --- | --- |
| CJK characters | 0.75 tokens/char |
| English/Latin prose | 5 chars/token |
| Code | 3.5 chars/token |
| JSON/YAML/config | 3 chars/token |
| Logs, number tables, IDs, hashes, URLs | 2.2 chars/token |
| Per message framing | +4 tokens |

On 16 fixtures (8 used to set the rates, 8 written afterwards) the reference implementation was +2.1% overall versus −30.9% for a universal chars ÷ 4. Each calibration fixture was within ±7%; held-out fixtures were within ±15% except a numeric CSV at −25%. Fixtures are small and synthetic, so this is not an error bound. Run `node dev/src/calibrate.js` to reproduce.

## Progress bar and handoff-priority labels

- 20 blocks, 5% per block, from the **unrounded** usage `u`: `u = 0` → 0 blocks; `0 < u < 100` → `floor(u/5 + 0.5)` clamped to 1..19; `u ≥ 100` → 20. Half rounds up. A full bar never appears below 100%.
- The numeric percentage is shown separately, rounded to a whole number (`<1%` below 1) and never capped. The bar can look identical on either side of a threshold (49.9% and 50% both draw 10 blocks); the priority word comes from the unrounded number.
- Partial coverage (summarized or truncated history, or attachments/images whose content is not loaded) replaces LOW/MEDIUM/HIGH/CRITICAL with `UNKNOWN (partial history)`, `UNKNOWN (unmeasured attachments)`, or both. The percentage and bar are the counted text against the planning budget and are labeled partial. The skill does not call the figure a lower bound, because summarized or truncated history may not correspond to what the server holds. The recommendation scales only with the counted share: below 70% "Consider /handoff before substantial work"; 70% to below 90% "Run /handoff before starting another major task"; 90% or more "Run /handoff now before continuing substantial work", each followed by what is not counted.
- An earlier version labeled such cases `Risk: LOW (lower bound)` while recommending a handoff, and implied the number was a proven floor. That was misleading and was replaced.

## Field report: few turns, long repeated drafts

A tester ran the installed skill in a ChatGPT Work chat opened the previous afternoon with fewer than 50 turns, in which the assistant had printed at least three full versions of a patent application and some "context optimization" content. It reported `~130k tokens (partial)`, `~102% (counted text only)`, `Risk: UNKNOWN` (partial history, unmeasured attachments), and a recommendation to run `/handoff`. The transcript is not available, so none of the following was checked against it.

**Is the magnitude plausible?** It can be. Using the rates measured here, a 10,000-word English draft is roughly 11k tokens and a 20,000-character Chinese draft roughly 14k. Three such drafts are about 35–45k tokens, so ~130k needs substantially more printed text than three drafts of that size: longer drafts, more than three printed versions, large pasted inputs, or long optimization output. A low turn count does not argue against it (a regression test builds a 30-message chat of full drafts above 100k tokens), and repeated drafts are not deduplicated, because every printed copy is part of the visible transcript. Two cautions apply:

- A model applying the rate table by judgment to 100k+ tokens of text is doing a rough size guess, not counting, so the figure is an order of magnitude, not a measurement.
- A count above what the model can plausibly see, reported together with "partial", suggests the number mixes what was visible with what was inferred. The skill already forbids extrapolating over unseen text (and now says so more directly), but it cannot enforce that.

**What the figure does not show.** It says nothing about ChatGPT's internal compaction, retrieval, memory, or backend token usage. If compaction happened without anything being printed, the skill has no way to know, and the active context could be smaller or larger than the visible transcript. Printed "context optimization" text counts like any other message; an internal optimization step does not count at all.

**Wording found to be too easy to misread.** The partial note said "counts accessible text only" and "actual usage may be higher or lower", but did not say that the percentage is not ChatGPT's token usage, or that internal compaction is not inspected, and nothing explained the visible/compaction/backend distinction to the model. Changes:

- `SKILL.md` gained a short "What the number is, and is not" section: visible text vs. internal compaction vs. actual backend usage, every printed copy counts once, turn count and age are not evidence either way, never say compaction happened unless a summary or truncation marker is visible, never count or subtract hidden state.
- The partial, unmeasured, and combined notes now read "Counts visible text only, not ChatGPT's backend token usage …" (with "or internal compaction" when history is partial).
- With full coverage and visible text at or above 100%, the note is now "Visible text exceeds the planning limit; backend usage is unknown, and ChatGPT may compact or truncate internally, which this skill cannot see." The risk label and recommendation are unchanged.
- Rates, thresholds, the 128k default, the bar rule, and the UNKNOWN behavior for partial or summarized history are unchanged. Two regression scenarios (`long-drafts-partial`, `long-drafts-complete`) and `dev/test/field-report.test.js` cover the report's shape with synthetic text.

**Why nothing was recalibrated.** One report gives a reported number and no ground truth, so it cannot say whether the rates are off.

**Data that would justify recalibration**

1. *Rates and the per-message overhead:* a set of real, exported ChatGPT transcripts (English, Chinese, code-heavy, tool-heavy, long-draft chats) with an `o200k_base` token count for each, and the skill's reported figure for the same transcript run several times, to separate rate error from run-to-run variation. Dozens of transcripts per content type would be needed before changing a rate, and the held-out set should stay unseen until the change is made.
2. *Model-applied error at large sizes:* the same long transcripts split at 10k, 50k, 100k, and 150k tokens, to see how the model's rough sizing degrades.
3. *Thresholds and the 128k planning limit:* observations of when a given ChatGPT surface and model actually start losing earlier content (for example, a detail from turn 1 that can no longer be recalled), paired with the visible-transcript size at that point. Without a documented measurement from ChatGPT itself, thresholds can only be tuned to those behavioral observations. They cannot be validated against real token counts.
4. *Compaction behavior:* whether and when ChatGPT summarizes or truncates silently, ideally from OpenAI documentation. This would show whether a visible-transcript percentage tracks active context at all after compaction.

## Remaining limits

- Whether ChatGPT's server-side context matches what the model can see (truncation, hidden summaries, file retrieval) is undocumented.
- How faithfully a model applies the rate table, and the bar rule, in each ChatGPT surface is only checked manually.
- The heuristic is calibrated on small synthetic fixtures and underestimates number-dense tables.
- `saved_limit` requires editing the uploaded skill's text or re-uploading.
- The documented 500k default is a single product- and model-specific figure checked on 2026-10-23. It can go stale, other Work models have no documented window here, and no platform runtime metadata for the model has been seen, so in practice the model is known only through `model=`.
- A model switch the user doesn't mention is invisible to the skill; without `model=` or runtime metadata it falls back to the default budget rather than guessing.
- The 128k default heuristic and the 50/70/90 thresholds are planning policy. Neither has been validated against when a ChatGPT Work model actually starts losing earlier content, so for a model whose real window is smaller than 128k, LOW can be optimistic.
- The sizing procedure is an instruction, and a language model applying it can still miscount or vary between runs; the skill has no transcript tokenizer or access to backend context usage, and no cross-model accuracy is claimed. The Luna ~10k case is not fixed or verified until the updated ZIP is uploaded and retested in ChatGPT Work.
- The `model=` argument, the `Model:` line, the new labels, and the default-budget guidance have not been tested in live ChatGPT, and no independent model has been run against the updated skill text. Whether the ~5x oversizing on Luna recurs, and why, is unknown; the counting procedure is a mitigation, not a guarantee.
